## Review A（Reviewer 1）

### 论文概述

MRP-Fuzz 的目标是通过一个两阶段模糊测试流程发现 Linux 内核中的数据竞争。第一步生成潜在的 Syzkaller 模式，然后分析其中的 may-race pairs，即可能发生竞争的数据访问。第二阶段选择最有希望的模式，以多种调度方式执行，使数据竞争得以显现。论文在 8 个模块上进行了评估。

### 技术正确性

**3. 存在可修复的重大问题**

实现细节难以理解，因为 artifact 并不完整，而且论文将 LLM 作为针对 Syzkaller 种子的黑盒变异算子使用。

论文没有独立评估基于 LLM 的 Syzkaller 变异所带来的收益。与相关工作相比，核心收益可能仅来自第一个组件，因为它发现了更有趣的交互；也可能核心贡献来自调度组件。没有消融实验，就很难判断哪个方面贡献最大，以及这些组件之间究竟存在什么差异。

LLM 的使用成本不清楚，也没有进行比较。当机制依赖外部 LLM 服务时，必须量化其成本和硬件需求，才能进行公平比较。

### 科学贡献

**3. 创建了可推动未来研究的新工具**
**5. 发现了有影响力的漏洞**

MRP-Fuzz 的主要贡献是将数据竞争搜索拆分为不同阶段。第一阶段利用 LLM 生成有针对性且有趣的访问对，以识别潜在交错；第二阶段尝试触发这些交错。

基于 LLM 的输入生成器和调度器都是有趣的组件，应分别评估。

将 MRP 声称为全新贡献有些言过其实，因为已有工作已经定义并分析过类似的 may-race 条件。甚至 TSan 也会记录访问，然后异步探索交错。

KRACE 和 CONZZER 都包含某种“先记录、后分析调度”的概念。例如，KRACE 将 happens-before 表示为 DAG 供后续分析，其检查器与状态探索是解耦的。其他一些工作也有类似思想。因此，作者应降低关于 MRP 新颖性的表述，或者更准确地解释其差异。

### 表达质量

**2. 存在轻微表达问题**

主要问题是论文过度声称 MRP 的新颖性。

## Review B（Reviewer 2）

### 论文概述

内核数据竞争 fuzzer 会把大量时间浪费在不太可能产生数据竞争的输入上。本文提出 MRP-Fuzz，将输入生成与线程调度解耦。其关键思想是 May-Race Pair：系统尝试识别可能导致冲突的 syscall group，即在较小时间范围内访问相同内存位置的操作。系统还提出 LLM 辅助的语义变异器，从 Syzkaller 生成的输入中获取 MRP。MRP-Fuzz 检测到许多新的数据竞争，其中一些具有危害，部分问题已得到开发者确认。

### 技术正确性

**1. 未发现明显缺陷**

MRP 背后的总体思想很直观，已有工作也表明 LLM 能够对内核代码进行语义推理，尽管那些工作研究的是其他领域或任务。

### 科学贡献

**6. 在成熟研究领域中提供了有价值的推进**

与 ConFuzz、SegFuzz 等现有 fuzzer 相比，该工作显著提高了数据竞争检测效果，并借此发现了新的有害数据竞争。

### 表达质量

**2. 存在轻微表达问题**

- 论文需要与 Snowboard 进行更详细、更细致的比较。

### 给作者的评论

感谢投稿。总体而言，这项工作有许多值得肯定之处：核心思想直观，系统工程实现看起来扎实，结果也很有潜力。不过，我有以下意见：

1. 阅读本文时，我不断想到 Snowboard（SOSP 2019，论文已将其列为文献 [21]）。MRP 的关键思想看起来与 Snowboard 提出的 Potential Memory Communication（PMC）非常接近。Snowboard 对 PMC 的描述是：若要在线程间形成 PMC，需满足：线程 A 执行一次写访问；线程 B 执行一次读访问；两次访问的内存区域重叠；并且线程 A 的写入把内存更新为不同于线程 B 顺序执行时本应读到的值。

   我看到的差异是 MRP 还考虑了时间接近性。这是否是两种思想之间唯一的差异？Snowboard 同样将线程调度与输入生成解耦，并像 MRP-Fuzz 一样使用 PMC 作为调度提示。论文应更明确地将这一思路归功于既有工作，并详细说明两者的细微差别。若在你们的 fuzzer 中使用基于 PMC 的方案，评估结果会是什么样？

2. 第 4 节设计还需要完善。我不清楚输入生成引擎如何检测内核对象或资源冲突，以及检测粒度是什么。你们是否像 Snowboard 一样使用 QEMU 记录每次内存访问，还是使用其他方法？设计部分应对此作出澄清。

   此外，LLM 辅助语义变异器的输入究竟是什么？是 syscall 或内核源代码、内存访问模式和 syscall group 吗？图 1 还提到了一些有效性检查，但我不确定正文是否解释了这些检查。

3. 在线程调度方面，对于某个 MRP 特别有趣、但当前阈值不足以纳入它的情况，你们是否考虑过 fallback 机制？这种机制可能有助于发现更多潜在数据竞争。

4. 评估在运行时间维度上很全面。不过，与完全随机的调度相比，使用 LLM 的货币成本是多少？

## Review C（Reviewer 3）

### 论文概述

MRP-Fuzz 是一个用于识别 Linux 内核并发缺陷的 fuzzer。其核心思想是只对高质量模糊测试输入使用调度器，而不是对每个输入都使用调度器，从而提高模糊测试效率。

作者提出了 May Race Pair（MRP）这一新概念。MRP 表示一对很可能导致数据竞争、因而应尽可能覆盖的操作。基于“最大化 MRP 数量将带来更多数据竞争发现”的假设，模糊测试引擎使用 MRP 作为反馈信号。

### 技术正确性

**4. 存在实质性重大问题**

#### 数据竞争的定义

MRP-Fuzz 对数据竞争的定义与既有工作不一致。既有工作 [1] 要求冲突访问之间不存在 happens-before 关系，才构成数据竞争。相比之下，MRP-Fuzz 在第 2.1 节中的定义要宽泛得多，因为它将 happens-before 关系视为与定义正交。

偏离传统数据竞争定义并非绝对不可接受，但我在这里看不出这样做的明确收益。相反，更宽泛的定义可能提高缺陷检测的误报率。

一个具体例子是内核中广泛使用的引用计数。假设线程 T0 将引用计数初始化为 1，线程 T1 将其递增，随后 T0 读取它。该场景符合 MRP-Fuzz 的定义：“来自不同线程、访问相同或重叠内存范围的两次访问，且至少一次为写。”然而，这显然不是缺陷 [2]，在传统定义下也不会被视为数据竞争。

引用计数只是一个例子。使用 cmpxchg 的无锁更新、RCU，以及用于统计信息的弱同步计数器等常见模式，也会被 MRP-Fuzz 分类为数据竞争。

鉴于这些模式在内核中使用极其广泛，我原本预期 MRP-Fuzz 会报告大量数据竞争，其中既有有害的，也有良性的。然而 MRP-Fuzz 仅报告了 187 个数据竞争，这个数字小得出乎意料。这使人怀疑这些数据竞争是如何识别的，以及评估是否一致采用了上述宽泛定义。

#### 动态时间阈值控制

第 3.3 节使用自适应时间阈值是一个新颖且有趣的方法，其设计动机在高层次上是合理的，但必须有实验支持这一直觉。

作者认为，由于不同程序逻辑中的竞争窗口长度不同，时间阈值应动态调整而非固定。该论点在直觉上有说服力，但仍需实证评估，以证明动态调整确实提高了缺陷发现效果。

具体而言，消融实验应将自适应阈值同时与固定阈值和随机阈值比较。这样才能量化自适应机制的贡献，并验证作者的直觉。

没有这样的评估，就很难判断第 3.3 节的设计是否确有必要，还是更简单的阈值策略也能达到类似效果。

#### 与现有工作的比较

论文缺少支撑最后一项贡献声明所需的信息，因而无法证明 MRP-Fuzz 优于现有方法。

第一，我没有找到 MRP-Fuzz、SegFuzz 和 CONZZER 在可比内核版本上评估的信息。MRP-Fuzz 运行在 2025 年 9 月发布的 Linux 6.17 上，而 SegFuzz 和 CONZZER 分别使用 2023 年 2 月的 v6.2 和 2019 年 11 月的 v5.4。跨越约两年和六年的不同代码库进行比较，对 fuzzer 相对效果的说明力有限。作者应明确列出各个 fuzzer 使用的内核版本，理想情况下应在同一内核版本上评估所有方法。否则，图 7 可能误导读者，使其误以为 MRP-Fuzz 与其他方法是在同一内核版本上比较的。

第二，从公开源代码看，SegFuzz 似乎无法完整复现。特别是，SegFuzz 论文描述的基于 VM 的断点机制和强制调度机制似乎没有在公开代码中实现。从 GitHub 仓库运行 SegFuzz，看起来与“使用旧版 Syzkaller 测试旧版内核”区别不大。如果作者不进一步澄清，图 7 可能具有误导性：它看起来是在证明 MRP-Fuzz 设计比 SegFuzz 设计覆盖更多 MRP，但实际比较的可能是完整的 MRP-Fuzz 与不完整或差异很大的 SegFuzz 实现。

作者应澄清：（1）每项比较使用的确切内核版本；（2）公开的 SegFuzz 实现是否包含原论文评估过的全部组件；（3）图 7 是否在等价实验设置下比较了各项设计。没有这些信息，我认为现有结果不足以支持 MRP-Fuzz 优于现有方法的结论。

[1] Foundations of the C++ Concurrency Memory Model
[2] Linux Kernel Memory Consistency Model（LKMM）

### 科学贡献

**3. 创建了可推动未来研究的新工具**
**5. 发现了有影响力的漏洞**

第一项贡献声明似乎不成立。

将输入生成与线程调度解耦并不是一种新范式。这是一种常见方法，多个并发 fuzzer（包括 Ozz 和 SegFuzz）已经展示过其效果。特别是，SegFuzz 使用了类似策略：它并不对每个生成输入都进行调度，而是先执行不带调度的传统 syscall fuzzing；识别出可能有趣的新交错之后，再使用基于 VM 的断点进行调度。

因此，“我们提出了一种新的内核并发模糊测试范式：解耦输入生成与线程调度”这一声明似乎没有新颖性，因为既有工作已经探索过这一设计原则。

此外，使用潜在数据竞争作为模糊测试反馈也不是新概念。KRACE、SegFuzz 和 Ozz 等既有工作已经使用潜在数据竞争或竞争相关信息作为反馈，以指导并发模糊测试。

作者应澄清与这些方法相比的根本差异。特别是，如果新颖性来自 MRP 的具体定义，或来自如何用 MRP 选择性触发调度，就应更准确地陈述贡献，而不是把新颖性归于“解耦输入生成和线程调度”或“使用竞争相关反馈”这样的宽泛思想。

### 表达质量

**3. 存在重大但可修复的表达问题**

- MRP 的形式化定义不清楚。论文称“n 标识静态访问点，s 标识栈上下文”，但没有明确界定这两个术语。我推测静态访问点是程序计数器或源代码级访问位置，而栈上下文是函数调用栈而非栈内存。作者应精确定义这些术语，并解释实现如何表示和识别它们。

- “real data race”的定义不清楚。该术语在全文出现 23 次，但我没有找到定义；论文似乎也没有使用与之对应的 fake 或 unreal data race。鉴于这一差别对评估似乎很重要，作者应明确说明什么构成 real data race，以及它与其他检测到的冲突访问有何不同。

- 论文没有清楚陈述研究问题。明确列出研究问题有助于说明评估要验证哪些假设，以及各项实验如何支持论文声明。

- 论文没有提供清晰的威胁模型。作者应说明 MRP-Fuzz 旨在检测哪些类型的并发缺陷或竞争条件，以及对目标内核、执行环境、攻击者或程序行为作出了哪些假设。

## Review D（Reviewer 4）

### 论文概述

MRP-Fuzz 研究 Linux 内核数据竞争缺陷检测。该问题需要同时搜索 syscall 序列输入空间和线程交错空间，而现有内核并发 fuzzer 没有有效处理两者之间的关系。MRP-Fuzz 识别在短时间间隔内发生的冲突变量访问对，时间间隔由动态阈值决定；这些访问来自不同线程、访问重叠内存范围，且至少一次写共享内存。

在输入生成阶段，输入生成实例产生 syscall group，并在没有线程调度的情况下并发执行，以收集 MRP。系统使用 LLM 进行语义变异，生成更有趣的 syscall group。线程调度实例使用提取出的 MRP 并进行调度。

模糊测试期间，系统通过背压控制动态调节阈值，使各实例保持平衡，避免饥饿或过度并发。在线程调度方面，系统引入候选 MRP 优先级、历史感知上下文恢复和上下文感知交错调度。原型基于 Syzkaller 实现，并使用基于快照的 VM 重置。论文在 8 个 Linux 内核模块上测试，发现 187 个数据竞争，其中 59 个有害。消融评估表明 LLM 语义变异带来了 92.7% 的提升。

### 技术正确性

**1. 未发现明显缺陷**

我没有看到明显缺陷。MRP-Fuzz 的设计论证令人信服。

### 科学贡献

**3. 创建了可推动未来研究的新工具**
**6. 在成熟研究领域中提供了有价值的推进**

MRP-Fuzz 提出了一种新的并发模糊测试方法，以及一种新的、用于表示值得调度候选项的抽象。论文进行了全面评估，结果表明其比当前最先进的 fuzzer 更有效。

### 表达质量

**1. 表达无缺陷**

没有明显问题。论文写作良好且易于理解。

一个小问题：为什么 SegFuzz [27] 出现在参考文献中，但正文实际提到 SegFuzz 的地方都没有标注“[27]”？

### 给作者的评论

感谢向 S&P 投稿。这是一项有趣的工作，提升了 Syzkaller 发现并发缺陷的能力。研究问题动机充分，行文易懂。评估很强，尤其是比较了两个 LLM，并对 LLM 做了消融，从而清楚说明了 LLM 在语义变异中的作用。不过，我有以下意见和建议：

1. 论文声称的范围较宽，似乎涵盖所有并发缺陷；但时间属性（例如时间距离较短的访问对）只是并发缺陷的一部分。例如，锁相关缺陷可能跨越很长的时间，因此不会被当前分析覆盖。论文应讨论这些情况，并澄清所分析的并发缺陷范围。

2. 测试的 Linux 内核模块可以更具代表性，并扩展到更大的驱动。8 个模块中有 5 个是文件系统，包括软盘设备驱动。文件系统确实高度并发，但 GPU、摄像头等其他内核 I/O 驱动可能也高度并发。目前测试的设备驱动（TTY、声卡）相对较小。Syzkaller 能够模糊测试多种复杂 I/O 驱动，因此，如果生成 MRP 不存在其他限制，系统应当能够扩展到更复杂的 I/O 驱动。

3. “MRP-Fuzz 是第一个使用 LLM 对并发 syscall group 进行语义变异的内核并发 fuzzer”这一声明可能过强，因为文献 [41] 和 KnitFuzz [a] 都是由 LLM 驱动的内核 fuzzer，也都进行语义变异，而且 [a] 实际发现了竞争条件缺陷。建议更精确地限定这一声明。

   [a] CODASPY '26 KnitFuzz: LLM-guided Kernel Fuzzing via Context-Sensitive Socket System Calls

4. 论文应更清楚地说明 MRP-Fuzz 在解耦输入生成与线程调度方面的新颖性。例如，它与 SegFuzz [27] 有何根本区别？LLM 生成的 syscall group 确实有趣，而且不使用 LLM 的消融版本也优于 SegFuzz。论文开头可以改进，更突出这些贡献以及与既有工作的主要设计差异。由于 SegFuzz 同样探索内核线程交错，从高层看，新颖性问题一直要到读者读到第 7.6 节与既有方法的比较后才得到部分回答。
