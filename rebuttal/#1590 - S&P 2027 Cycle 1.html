Detecting data races in the Linux kernel requires searching both the input space and thread-interleaving space. Existing kernel concurrency fuzzers couple these two searches by exploring interleavings during fuzzing. However, most inputs generated by these fuzzers have little potential to trigger real races, and scheduling interleavings for such inputs causes a significant waste of testing effort.

In this paper, we propose MRP-Fuzz, a novel kernel concurrency fuzzing framework that decouples input generation and thread-interleaving exploration by introducing a new concept, May Race Pair (MRP). Unlike a real data race, whose variable access pair actually occurs concurrently, an MRP represents a conflicting variable access pair that occurs within a dynamically determined time threshold. During the fuzzing campaign, MRP-Fuzz performs pure input generation and collects triggered MRPs, which are used by our LLM-assisted semantic mutation to generate diverse syscall program groups. Then, MRP-Fuzz sets up a scheduling instance that consumes the collected MRPs and explores possible thread interleavings to confirm them as real races. Our scheduling integrates techniques including history-aware context recovery, context-aware interleaving scheduling, and candidate MRP prioritizing. We implement MRP-Fuzz for the Linux kernel and evaluate it on eight common modules in Linux 6.17. MRP-Fuzz finds 187 unique real data races, among which 59 are harmful. Compared to existing kernel concurrency fuzzers, MRP-Fuzz finds substantially more real races with more MRPs. We expect MRP-Fuzz to benefit kernel testing community by introducing a new concurrency fuzzing paradigm.

Ethics Considerations

This work studies kernel data-race detection using fuzzing in a controlled local testing environment. The discovered issues concern only open-source Linux kernel components, and we will follow responsible disclosure practices for security-relevant bugs. The tool may be used to find security bugs, but its intended use is defensive testing and improving kernel reliability.

Generative AI Usage Considerations

Generative AI was used in two ways. First, the proposed system uses large language models as part of its research methodology: LLMs are used as semantic mutation assistants to help modify syscall program groups. We discuss this use in the paper and evaluate the system under controlled experimental settings. Second, generative AI tools were used for editorial assistance during manuscript preparation, such as improving wording, grammar, and clarity. All AI-generated text or suggestions were inspected and revised by the authors, who take full responsibility for the factual correctness, accuracy, originality, citations, figures, experiments, and conclusions of the submission.

Review #1590A

Paper Summary

MRP-Fuzz has the goal of finding data races in the Linux kernel through a two-phased fuzzing process. The first step generates potential syzkall patterns that are then analyzed for may-race-pairs, data access that may race. The second phase then uses the most promising patterns to schedule diversely allowing data races to emerge. It has been evaluated on 8 modules.

Technical Correctness

3. Fixable Major Issues

Technical Correctness Comments

The implementation details are hard to follow as the artifact is not complete and the LLM is used as a black box mutation operator for the syzcaller seeds.

The benefits of the LLM-based syzcaller mutation are not evaluated independently. The core benefit compared to related work could be just this first component that discovers more interesting interactions. Alternatively, the core contribution could come from the scheduling component. Without an ablation study, it is challenging to infer which aspect brings the main contribution and what these differences are.

The cost of LLM usage is unclear and not compared. When comparing LLM-based mechanisms that rely on external LLM services, it must be quantified what their cost and hardware needs are to provide a fair comparison.

Scientific Contribution

3. Creates a New Tool to Enable Future Science

5. Identifies an Impactful Vulnerability

Scientific Contribution Comments

The main contribution of MRP-Fuzz is to break the search for data races into different phases. The first phase leverages an LLM to generate interesting focused pairs to detect potential interleavings. The second phase then tries to trigger these interleavings.

Both the LLM-based input generator and the scheduler are interesting components that should be evaluated individually.

The claim that MRP is a novel contribution is a bit overclaiming as these may-race conditions have been defined and analyzed in prior work. Even TSan records accesses and then explores interleavings asynchronously.

KRACE and CONZZER both have some notion of recording and later analysis of schedules. For example, KRACE presents happens-befoer as DAG for later analysis. The checker is decoupled from state exploration. Several other work have similar notions. The authors should therefore tone down the claim of novelty for MRP (or explain the differences more precisely).

Review #1590B

Paper Summary

Kernel data race fuzzers waste a lot of time on inputs that are less likely to yield data races. This paper presents MRP-Fuzz, a system that decouples input generation and thread scheduling. The key idea is "May-Race Pair" where the system attempts to identify syscall groups that would lead to a conflict (i.e., access same memory locations within a small time bound). The system proposes an LLM-assisted semantic mutator to guage MRPs from incoming syzkaller generated inputs. Using MRP-Fuzz, the system was able to detect many new data races (some of which are harmful) and some of them have been confirmed by developers.

Technical Correctness

1. No Apparent Flaws

Technical Correctness Comments

The overall idea behind MRP is intuitive and prior works have shown that LLMs have the ability to semantically reason about kernel code (albeit in other domains/tasks).

Scientific Contribution

6. Provides a Valuable Step Forward in an Established Field

Scientific Contribution Comments

The work significantly improves data race detection effectiveness compared to existing fuzzers like ConFuzz and SegFuzz. With this improved effectiveness, the system was also able to discover new harmful data races.

Comments to Authors

Thanks for this submission. Overall, there are many aspects to like about the work. The core idea is intuitive. The system looks well-engineered and the results are highly-promising. That being said, I have the following comments:

  1. While reading this paper, I was constantly reminded of Snowboard (SOSP19, which has been duly cited in the draft as [21]). The key idea of MRP seems very close to the "Potential Memory Communication" (or PMC) presented in that paper. The Snowboard paper says:

"For a PMC between threads to occur, 1) thread A has to make a write memory access, 2) thread B has to make a read memory access, 3) the memory regions of the two accesses must overlap, and 4) the write access by thread A has to update the memory area with a different value from what the read access by thread B would have fetched if thread B ran sequentially."

The difference I see is that MRP additionally considers temporal closeness. Is that the only difference in the ideas? The Snowboard also decouples thread scheduling and input generation, and uses PMCs as a hint for scheduling (just like MRP-Fuzz). This approach should be attributed to prior work more clearly. A more detailed and nuanced difference in the ideas needs to be also elaborated. What would a PMC-based evaluation look like for your fuzzer?

  1. The design section 4 can use some work. It was not clear to me how and at what granularity the kernel object/resource conflict is detected by the input generation engine. Do you use QEMU to log every memory access (like Snowboard does), or a different approach? A clarification in the design would be useful to understand this aspect more clearly.

Additionally, what is the input to the "LLM-assisted semantic mutator"? Is it the source code of the syscall/kernel, memory access patterns, and syscall groups? Figure 1 also mentions some validity checks, but I'm not sure this was explained.

  1. On thread scheduling, have you considered introducing a fallback mechanism for cases where the MRP is particularly interesting, but the threshold is not sufficient at that time? This could be interesting to detect further potential data races.

  2. The evaluation is comprehensive in the time dimension. However, I wonder what is the monetary cost of using the LLMs, versus a completely random schedule?

Review #1590C

Paper Summary

MRP-Fuzz is a fuzzer designed to identify concurrency bugs in the Linux kernel. The core idea is to selectively apply a scheduler to high-quality fuzzing inputs rather than to every input, thereby improving fuzzing efficiency.

The authors propose a new concept, May Race Pair (MRP), which represents a pair of operations that is highly likely to cause a data race and therefore should be maximized. Based on the hypothesis that maximizing the number of MRPs will lead to more data race detections, the fuzzing engine uses MRP as a fuzzing signal.

Technical Correctness

4. Substantial Major Issues

Technical Correctness Comments

Definition of Data Races

MRP-Fuzz's definition of a data race does not align with prior works. Prior works [1] require that no happens-before relation exists between the conflicting accesses to constitute a data race. In contrast, MRP-Fuzz's definition of a data race (Section 2.1) is much broader, as it treats happens-before relations as orthogonal to the definition.

Although deviating from the conventional definition of a data race can be acceptable, I do not see a clear benefit to doing so in this case. On the contrary, this broader definition can lead to a higher rate of false positives in bug detection.

A concrete example is a reference counter, which is widely used throughout the kernel. Suppose thread T0 initializes a reference count to 1, thread T1 increments it, and T0 subsequently reads it. This scenario satisfies MRP-Fuzz's definition of a data race: "... two accesses from different threads to the same or overlapping memory range, where at least one access is a write." However, this is clearly not a bug [2] and would not be considered a data race under the conventional definition.

Reference counting is just one example. Other common patterns, such as lockless updates using cmpxchg, RCU, and loosely synchronized counters for statistics, would also be classified as data races under MRP-Fuzz's definition.

Given how extensively these patterns are used in the kernel, I would expect MRP-Fuzz to report a large number of data races, including both harmful and benign ones. However, MRP-Fuzz reports only 187 data races, which seems surprisingly small to me. This raises questions about how the reported data races were identified and whether the broader definition is actually being applied consistently in the evaluation.

Dynamic Time-Threshold Control

Applying an adaptive time threshold (Section 3.3) is a novel and interesting approach, and the rationale behind this design decision is reasonable at a high level. However, experiments are necessary to support this intuition.

The authors argue that the time threshold should be dynamically adjusted rather than fixed because the lengths of race windows vary across different program logic. Although this claim is intuitively convincing, it requires empirical evaluation to establish whether dynamic adjustment actually improves bug-finding effectiveness.

Specifically, an ablation study should compare the adaptive time threshold against both a constant threshold and a randomized threshold. Such a comparison would help quantify the contribution of the proposed adaptive mechanism and validate the authors' intuition.

Without such an evaluation, it is difficult to determine whether the design described in Section 3.3 is necessary for improving bug-finding effectiveness, or whether a simpler thresholding strategy would perform similarly.

Comparison with Existing Work

The necessary information is lacking to support the final contribution claim that MRP-Fuzz outperforms existing approaches.

First, I could not find a comparable kernel version on which MRP-Fuzz, SegFuzz, and CONZZER are evaluated. MRP-Fuzz runs on Linux kernel v6.17, released in September 2025, whereas SegFuzz and CONZZER use v6.2 (February 2023) and v5.4 (November 2019), respectively. Comparing results across different code bases, with gaps of approximately two and six years, provides limited insight into the relative effectiveness of the fuzzers. The authors should clearly specify the kernel version used for each fuzzer and, ideally, evaluate all approaches on the same kernel version. Otherwise, Figure 7 could misleadingly suggest that MRP-Fuzz achieves better metrics than the other approaches on the same kernel version, which is not the case.

Second, SegFuzz does not appear to be fully reproducible from the publicly available source code. In particular, the VM-based breakpoint mechanism and forced-scheduling mechanism described in SegFuzz do not appear to be implemented in the released source code. Moreover, running SegFuzz from its GitHub repository seems to be a little different from running an older version of Syzkaller against an older kernel. Without further clarification from the authors, Figure 7 could therefore be misleading. It may appear to demonstrate that the MRP-Fuzz design achieves better MRP coverage than the SegFuzz design, when the comparison may actually be between the full MRP-Fuzz implementation and an incomplete or substantially different implementation of SegFuzz.

The authors should clarify (1) the exact kernel versions used for each comparison, (2) whether the publicly available SegFuzz implementation contains all components evaluated in the original work, and (3) whether Figure 7 compares the proposed designs under equivalent experimental settings. Without this information, I do not think the results are sufficient to support the claim that MRP-Fuzz outperforms existing approaches.

[1] Foundations of the C++ Concurrency Memory Model [2] Linux Kernel Memory Consistency Model (LKMM)

Scientific Contribution

3. Creates a New Tool to Enable Future Science

5. Identifies an Impactful Vulnerability

Scientific Contribution Comments

The first contribution claim does not appear to hold.

Decoupling input generation from thread scheduling is not a new paradigm. It is a common approach as well as its effectiveness has already been demonstrated by several concurrency fuzzers, including Ozz and SegFuzz. In particular, SegFuzz adopts a similar strategy. Rather than applying scheduling to every generated input, it first performs conventional syscall fuzzing without scheduling and then applies scheduling through VM-based breakpoints when it identifies a potentially interesting new interleaving.

Therefore, the claim that "we propose a new paradigm for kernel concurrency fuzzing: decoupling input generation and thread scheduling" does not seem to be novel, as this design principle has already been explored in prior work.

Furthermore, using potential data races as fuzzing feedback is also not a new concept. Prior work, including KRace, SegFuzz, and Ozz, has used potential data races or race-related information as feedback to guide concurrency fuzzing.

The authors should therefore clarify what is fundamentally different from these existing approaches. In particular, if the novelty lies in how MRP is defined or how it is used to selectively trigger scheduling, the contribution should be stated more precisely rather than attributing novelty to the broader idea of decoupling input generation from thread scheduling or using race-related feedback.

Presentation

3. Major but Fixable Flaws in Presentation

Presentation Comments

  • The formal definition of MRP is unclear. It states that "n identifies the static access site, and s identifies the stack context," but neither static access site nor stack context is explicitly defined. My best interpretation is that a static access site refers to a program counter or source-level access location, while a stack context refers to a function call stack rather than stack memory. The authors should provide precise definitions of these terms and explain how they are represented and identified in the implementation.

  • Definition of "real data race." The term real data race appears 23 times throughout the paper, but I could not find a definition. Moreover, the paper does not appear to use the corresponding notion of a fake or unreal data race. Given that the distinction seems important to the evaluation, the authors should explicitly define what constitutes a "real data race" and explain how it differs from other detected conflicting accesses.

  • The paper does not clearly state its research questions. Explicit research questions would help clarify what hypotheses the evaluation is intended to investigate and how the experiments support the paper's claims.

  • The paper does not provide a clear threat model. The authors should specify what types of concurrency bugs or race conditions MRP-Fuzz aims to detect, as well as any assumptions it makes about the target kernel, execution environment, or attacker/program behavior.

Comments to Authors

Strengths

  • Finding 39 real-world bugs is a significant result.

  • The adaptive time threshold is an interesting idea that could improve the efficiency of concurrency fuzzing.

  • Using data races as fuzzing feedback is a general idea that could potentially be applied beyond kernel fuzzing and to other domains.

  • The artifact provides a strong foundation for understanding and further evaluating the work.

Weaknesses

  • The novelty of the proposed approach is not sufficiently established.

  • The experimental comparison with prior approaches is difficult to interpret due to differences in kernel versions and potentially incomplete implementations of existing tools.

  • The paper uses a broader definition of data races than conventional definitions without sufficiently justifying why this definition is appropriate or beneficial.

  • The paper does not clearly state its research questions, making it difficult to understand what hypotheses the evaluation is intended to validate.

Review #1590D

Paper Summary

MRP-Fuzz addresses the detection of data race bugs in Linux kernel which requires researching in both the syscall sequence input space and thread interleaving. The existing kernel concurrency fuzzer does not effectively couple these two. MRP-fuzz identifies conflicting variable-access pair that occur within a short time interval (a dynamically determined time threshold), and work from different threads overlapping a memory range with at least one write to the shared memory range. For input generation, input-generation instance are syscall groups execute them concurrently without thread scheduling for collection of MRPs. LLM is used for semantic mutation for generating more interesting syscall groups. Thread-scheduling instance uses the extracted MRPs and schedule them.

During fuzzing it uses a backpressure-guided control to dynamically adjust the threshold to keep the instances balanced to avoid starvation or over concurrency. For thread scheduling, it introduces candidate MRP prioritizing, history aware context recovery, and context aware interleaving scheduling. The prototype is built on Syzkaller with snapshot based VM resets. It is tested on 8 linux kernel modules. It found 187 data races among which 59 are harmful. There is ablation evaluation show LLM contributes 92.7% semantic mutation.

1. No Apparent Flaws

Technical Correctness Comments

I don't see apparent flaws. The design of MRP fuzz is convincingly justified.

Comments to Authors

Thanks for submitting to S&P. This is an interesting work improving Syzkaller's ability in finding concurrency bugs. The research problem is well-motivated and the writing is easy to follow. The evaluation is strong, especially that it compares two LLMs, did the ablation study of the LLM, making the role of LLM in semantic mutation clear. However I have a few comments and suggestions to improve the paper.

  1. The scope claimed in the paper is broadly covering all concurrency bug, but the temporal attributes ( e.g., access pairs with shorter temporal distances) is only a part of concurrency bug. For example, lock related bugs that may temporally span far from each other (thus not covered in your analysis). These cases should be discussed and clarify the scope of concurrency bug that the analysis covers.

2.The tested Linux kernel modules can be more representative and scale to larger drivers. Five out of eight of the studied modules are file system, including floppy drive device driver. File systems are concurrency-heavy, but other kernel modules like I/O device drivers (gpu, camera, etc) may be more concurrency heavy. the tested device drivers (tty, sound) are relatively small. Syzkaller is capable to fuzz a wide range of complex I/O device drivers, so if there is no other limitations in producing the MRP pairs, it should be scalable to more complex I/O device drivers.

  1. The claim that "MRP-FUZZ is the first kernel concurrency fuzzer to use LLMs for semantic mutation of concurrent syscall groups." may be too strong, given that [41] and KnitFuzz [a] are both LLM-powered kernel fuzzers (and both do semantic mutation) and [a] actually found race condition bugs, I recommend scoping the claim more precisely.

  1. The novelty of MRP-Fuzz, in decoupling input generation and thread scheduling, should be clarified in writing. The beginning of the paper can be improved in presentation to better highlight these contributions and main design diversions from prior work.
