% ---- P1: 数据竞争的危害 ----
数据竞争是操作系统内核中最具破坏性的并发缺陷之一。当两个执行上下文在缺乏正确同步的情况下并发访问同一内存位置，且至少一方为写操作时，程序行为就可能变得不可预测。对于 Linux 内核而言，这类错误不仅会触发文件系统元数据损坏或潜在数据丢失~\cite{cve-2022-49414,cve-2022-49171}、内存破坏~\cite{cve-2022-49554} 和 use-after-free~\cite{cve-2022-50145,cve-2025-40318}，还可能进一步演化为权限提升等高危安全漏洞~\cite{cve-2021-4202,cve-2023-0266,dirtycow}。随着 Linux 内核规模与并发程度持续增长，在庞大而高度共享的执行环境中及时暴露数据竞争，已经成为内核可靠性与安全性保障中的核心问题之一。

% ---- P2: 发现数据竞争很难 ----
然而，与传统单线程缺陷不同，数据竞争只有在特定输入和特定线程交错同时满足时才会暴露：前者决定执行能否到达竞争双方，后者决定两侧访问能否在并发执行中形成实际重叠。因此，数据竞争发现本质上是对输入与交错的联合搜索，这显著扩大了搜索空间，增加了其发现难度。

% ---- P3: 现有工作与核心不足 ----
针对数据竞争的发现问题，已有许多工作提出了不同的方法。最早的一些模糊测试工作主要沿输入这一单一维度进行探索~\cite{angora,fairfuzz,smartgreybox,superion,syzkaller,moonshine,difuze,charm,janus,hydra}，并借助 KCSAN、KTSAN 等 data-race checker~\cite{kcsan,ktsan} 在执行后帮助确认数据竞争的发生；然而，这类方法通常仍以顺序代码覆盖率作为程序反馈，缺乏对线程交错的直接刻画，因此在并发维度上的引导能力有限。另一类方法尝试先通过启发式分析缩小搜索空间，再围绕筛选出的重点候选进行调度验证。Razzer~\cite{razzer}、Snowboard~\cite{snowboard}、Snowcat~\cite{snowcat} 等工作属于这一方向：它们通过静态分析、通信线索或学习式优先级，将测试预算聚焦到更可能产生有效并发交互的输入或调度上。然而，这类方法所保留下来的信息通常并不是足够直接、足够细粒度、且可供后续阶段复用的运行时并发证据，因此即便经过筛选，后续仍需在较大的候选空间中继续探索，整体效率仍然受限。还有一类工作，如 KRACE~\cite{krace}、CONZZER~\cite{conzzer}、SegFuzz~\cite{segfuzz}、RFF~\cite{rff} 和近期的 LACE~\cite{lace}，则显式定义并发反馈，或在执行过程中嵌入线程调度与受控调度，以探索更丰富的交错情况。相比只做候选筛选的方法，这类工作能够更系统地推进并发探索；但其中大量交错并非都直接对应高价值的 race 候选，从而使 fuzzing 或 testing 主循环不得不持续承担高成本的调度搜索。总体来看，上述方法虽然路径不同，但都在不同程度上将发现“哪里可能存在竞争”和确认“竞争是否真实存在”耦合在同一流程中，使得 fuzzing 吞吐量容易受到调度开销的制约，也使发现阶段产出的信息难以自然支撑后续的集中验证、诊断与稳定重触发~\cite{aitia,cardshark}。

% ---- P4: 核心观点 ----
我们的核心观点是，应当将输入维度的探索与并发维度的探索解耦为两个独立阶段。我们不再要求 fuzzing 阶段直接找到已被确认的数据竞争，而是让它在自然并发执行中探索潜在的竞争访问对。这些访问对已经接近真实竞争：它们来自不同线程、作用于同一地址，且在时间上彼此接近，只是最终是否形成访问重叠仍有待验证。验证阶段随后利用每个访问对携带的上下文信息进行定向调度，以精确确认真实竞争。这种解耦使 fuzzing 阶段的吞吐量不再受调度开销拖累，同时也让后续调度具有明确目标，而不是在交错空间中盲目搜索。


% ---- P5: May-Race Pair ----
回顾数据竞争成立的四个必要条件：两次访问来自不同线程、作用于同一地址或重叠地址、至少一方为写、并且在时间上真正重叠。前三个条件可以在运行时直接观测，第四个条件则通常需要反复调度才能确认。我们将条件 (4) 从“访问在时间上真正重叠”松弛为“时间差不超过阈值 $\tau$”，即 $|t_1 - t_2| \leq \tau$，并据此定义 \emph{May-Race Pair}：满足条件 (1)--(3) 且时间差不超过 $\tau$ 的一对跨线程访问。这样的访问对已经满足数据竞争成立所需的大部分前提，唯一尚待确认的是是否真正形成访问重叠，而这留给后续验证阶段完成。May-Race Pair 的价值与阈值选择密切相关：阈值越小，候选通常越接近真实竞争，但数量也越少；阈值越大，候选数量增加，但噪声也随之上升。因此，我们采用启发式方法动态调整时间阈值，以在候选保留广度与后续验证开销之间取得平衡。

% ---- P6: 系统概述 ----
围绕 May-Race Pair，我们实现了一个两阶段系统。Fuzzing 阶段的目标是在自然并发执行中发现尽可能多的 May-Race Pair。我们以 $(\textit{VarName}_1,\textit{VarName}_2,\textit{CallStack}_1,\textit{CallStack}_2)$ 四元组定义并发覆盖度，并同时记录两端访问的时间信息，其中 VarName 标识共享访问的位置，CallStack 标识访问发生时的执行路径。该阶段通过两个机制推进候选发现：其一是基于共享资源的并发程序组生成，在执行前统一两个程序的关键资源参数，使其更可能操作同一内核对象；其二是基于 pair 的时序探索，根据已发现 pair 的时间信息调整执行时序，以在已知共享位置附近发现更多的 May-Race Pair。验证阶段则消费 fuzzing 阶段积累的 pair，对每个候选执行定向调度，使双方访问重叠，从而确认真实数据竞争。


% ---- P7: Contributions ----
总体而言，本文做出以下贡献：
\begin{enumerate}
    \item 我们指出现有内核并发 fuzzing 的根本限制不只是反馈不够精细，而是发现与确认被绑定在同一循环中，导致调度成本过早侵入 fuzz 主流程；为此，我们提出 May-Race Pair 作为连接发现、探索与验证的统一运行时证据对象。
    \item 我们围绕 May-Race Pair 设计了一套端到端框架，包括资源感知的并发程序组构造、pair 保留与筛选、基于 pair 的局部时序探索，以及基于 pair 的集中调度和验证机制，从而将高吞吐发现与高命中确认解耦。
    \item 我们在 Linux 内核上实现了该系统，并将其与代表性并发测试和并发 fuzzing 方法进行比较。结果表明，该设计能够更高效地产生高价值候选，并更自然地支持后续验证与稳定重触发。
\end{enumerate}
