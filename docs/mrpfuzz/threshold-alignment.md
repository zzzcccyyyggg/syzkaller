# MRPFuzz Threshold Alignment

This note records the threshold behavior expected by the paper and the current
repository implementation.

## Current Experiment Defaults

New MRPFuzz configs generated by `scripts/generate_config.py` use:

- `normal_threshold_micros = 10000`
- `enable_dynamic_threshold = true`
- `dynamic_threshold_initial_us = 2500`
- `dynamic_threshold_min_us = 500`
- `dynamic_threshold_max_us = 10000`
- `dynamic_threshold_eval_sec = 30`
- `widened_threshold_micros = 20000`

The same values are mirrored in `scripts/EXPERIMENT_RUNBOOK.md`,
`scripts/run_capability_24h.sh`, and the local follow-up helper
`scripts/defer_followup_experiments.py`.

If an executor request carries `timing_threshold_us = 0`, the executor fallback
is 10ms.

## Paper Algorithm

The paper defines an MRP as a conflicting cross-thread access pair whose
temporal distance satisfies:

```text
Delta t <= tau
```

In Section 3.3, `tau` is a dynamic admission-control threshold. Algorithm 1 is
implemented by `pkg/fuzzer/threshold_controller.go`:

- The fuzzer is the producer, the validator/scheduler is the consumer.
- The schedule-worthy corpus is the queue between them.
- At each control interval `Tc`, the controller observes:
  - `P`: newly produced MRP records,
  - `C`: consumed MRP records,
  - `Q`: pending MRP records.
- It maintains EWMA counts:
  - `Pbar = rho * Pbar + (1-rho) * P`
  - `Cbar = rho * Cbar + (1-rho) * C`
- It estimates buffered workload as `W = Q / max(Cbar, epsilon)`.
- It shrinks `tau` to `max(tau_min, gamma_shrink * tau)` when
  `W > Whigh && Pbar >= Cbar`.
- It grows `tau` to `min(tau_max, tau + DeltaTau)` when
  `Q == 0 || (W < Wlow && Pbar <= Cbar)`.

The paper parameters are now the controller defaults:

- `Tc = 30s`
- `Wlow = 10`
- `Whigh = 40`
- `rho = 0.8`
- `epsilon = 1`
- `gamma_shrink = 0.5`
- `DeltaTau = 0.05 * (tau_max - tau_min)`

## Implementation Mapping

The controller derives the paper variables from existing shared state:

- `P` comes from the delta of the fuzzer-side total MRP count.
- `C` comes from the delta of validator `processed_count`.
- `Q` comes from validator `pending_count`.

Validator stats are read from `threshold-state.json`. If the validator stats are
missing or stale, the controller has no fresh consumer observation and treats the
observable queue as empty (`C=0, Q=0`), which follows the paper's `Q == 0`
relaxation branch.

Timing exploration uses a related but separate threshold policy:

- Normal fuzz requests use the current dynamic threshold.
- Timing Phase 1 uses
  `max(current_dynamic_threshold * 8, widened_threshold_micros)`.
- Timing Phase 2 returns to the current dynamic threshold.

With the current generated configs, Phase 1 is never below `20000us`, while the
normal dynamic threshold is bounded to `[500us, 10000us]`.

## Historical Note

The 20260609 paper-result lineage was produced before this code alignment, when
the controller used a production backlog-watermark approximation with
`dynamic_threshold_eval_sec = 120`. Keep those artifacts as historical results;
new reruns should use the paper-matched controller and `30s` control interval.

## Remaining Naming Debt

`uaf-corpus.db`) for race/MRP logic. This is naming debt, not a threshold
behavior difference.
