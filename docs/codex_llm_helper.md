# Codex LLM-helper backend for MRPFuzz

This note documents the local Codex backend for the MRPFuzz LLM-helper seed
producer. The backend is implemented only on the producer side. `syz-manager`
continues to consume accepted seed groups from `experimental.llm_input_seed_dir`
and does not need to know which model produced them.

## Design

The input-exploration pipeline has three layers.

The seed producer selects recent MRP corpus entries, builds the module-specific
prompt, invokes an LLM provider, runs the local syzkaller parser/filter, and
writes accepted two-program groups as JSON files under `accepted/`.

The provider layer is responsible only for turning a system/user prompt pair
into a text response. The current providers are `deepseek` and `codex`.
`deepseek` calls the DeepSeek chat-completions endpoint. `codex` calls the local
`codex exec` CLI with a JSON schema and a read-only sandbox.

The fuzzing manager polls the accepted seed directory and enqueues valid
two-program groups as high-priority barrier input seeds.

This separation keeps GPT-5.4, GPT-5.5, and DeepSeek experiments comparable:
the entry selection policy, prompts, local checker, accepted-seed format, and
manager ingestion path stay identical across providers.

## Codex provider behavior

The Codex provider uses:

```bash
codex exec --ephemeral -C "$PWD" -s read-only -a never \
  --output-schema <schema.json> -o <last-message.json> -m <model> -
```

The prompt explicitly instructs Codex to act as a constrained JSON backend, not
as a repository-editing agent. The read-only sandbox and `never` approval policy
also prevent accidental writes during generation. The local checker remains the
source of truth for accepting or rejecting generated programs.

## Offline pilot

Run a bounded pilot with GPT-5.4:

```bash
python3 tools/llm-mutate-pilot/pilot.py \
  --provider codex \
  --codex-model gpt-5.4 \
  --config exp/jfs/exp-fuzz-llm-helper-promptscope-20260520-000539.cfg \
  --module jfs \
  --entries 8 \
  --variants-per-entry 2 \
  --timeout-sec 600 \
  --out paper/results/llm-mutate-pilot/jfs-codex54-smoke
```

Run the same pilot with GPT-5.5 by changing only the model and output directory:

```bash
python3 tools/llm-mutate-pilot/pilot.py \
  --provider codex \
  --codex-model gpt-5.5 \
  --config exp/jfs/exp-fuzz-llm-helper-promptscope-20260520-000539.cfg \
  --module jfs \
  --entries 8 \
  --variants-per-entry 2 \
  --timeout-sec 600 \
  --out paper/results/llm-mutate-pilot/jfs-codex55-smoke
```

The pilot writes prompts, raw model output, checker output, accepted seeds, and
summary statistics. Use it first to compare valid JSON rate, local accept rate,
and the shape of accepted programs before launching long fuzzing runs.

## Continuous producer

For a fuzzing run, point the manager config at a provider-specific seed
directory, for example:

```json
"llm_input_seed_dir": "/home/zzzccc/BASS/DDRD-syzkaller/paper/results/llm-mutate-continuous/jfs-codex54",
"llm_input_seed_poll_sec": 30,
"llm_input_seed_max_per_poll": 12
```

Then run the continuous producer:

```bash
python3 tools/llm-mutate-pilot/continuous.py \
  --provider codex \
  --codex-model gpt-5.4 \
  --config exp/jfs/exp-fuzz-llm-helper-promptscope-20260520-000539.cfg \
  --module jfs \
  --out paper/results/llm-mutate-continuous/jfs-codex54 \
  --entries-per-round 2 \
  --variants-per-entry 2 \
  --parallel-calls 1 \
  --poll-sec 120 \
  --timeout-sec 600
```

For GPT-5.5, use a separate seed directory and change only `--codex-model` and
the manager config's `llm_input_seed_dir`. This avoids mixing seeds generated by
different models.

## Experiment discipline

For a model comparison, keep the following fixed:

1. The same module config and enabled syscall list.
2. The same input-exploration budget and manager resource allocation.
3. The same entry selection parameters, such as `entries-per-round`,
   `variants-per-entry`, and `max-calls`.
4. The same local checker and module-specific policy.
5. Separate output directories for GPT-5.4, GPT-5.5, DeepSeek, and random
   controls.

Report both producer-side quality and fuzzing-side impact. Producer-side
quality includes valid JSON rate, local accept rate, and accepted seeds per
hour. Fuzzing-side impact includes MRP pairs, VarName pairs, new stacks per
VarName pair, and confirmed races after full validation.

## Model-comparison protocol

The reference protocol is the successful f2fs repaired-corpus run from
2026-05-23/2026-05-24. Use it as the default template for subsequent LLM-helper
comparisons.

### Fixed fuzzing setup

Keep the fuzzing mechanism identical across random and all LLM variants:

```json
"static_input_exploration": true,
"static_input_skip_builtin_seeds": true,
"random_baseline_mode": true,
"enable_object_linking": false,
"object_link_attempt_ratio": 0,
"enable_timing_exploration": false,
"timing_exploration_ratio": 0,
"enable_coverage_triage": false,
"enable_affinity_table": false,
"no_object_kccwf_namespace": false,
"isolate_kccwf_partner_objects": false
```

Use the repaired corpus without the internal kccwf path-randomization rewrite.
For filesystem modules, this keeps the state space close enough to the kccwf
mount namespace for validation replay while still allowing LLM variants to
change program structure, syscall order, and parameters.

The standard budget for model comparison is:

```text
fuzz VMs: 4
fuzz duration: 10 hours
manager LLM seed poll interval: 10 seconds
manager max seeds per poll: 32
producer entries per round: 8
producer variants per entry: 2
producer parallel calls: 4
producer max calls per generated program: 8
producer poll interval: 30 seconds
producer timeout: 600 seconds
```

The random control must use the same manager config with only the
`llm_input_seed_*` fields removed.

### Model matrix

Run each model in a separate workdir and seed directory. Do not mix accepted
seeds from different providers.

| Variant | Provider path | Model id | Thinking | Reasoning knob |
| ------- | ------------- | -------- | -------- | -------------- |
| Random | none | none | none | none |
| DeepSeek V4 Pro | `--provider deepseek` | `deepseek-v4-pro` | `disabled` | not sent when thinking is disabled |
| GPT-4 | `--provider codex` | exact GPT-4 model id used by `codex exec` | n/a | `--codex-reasoning-effort high` |
| Kimi 2.6 | `--provider kimi` | `kimi-k2.6` | `disabled` | not sent when thinking is disabled |

If a provider exposes a reasoning-effort knob that is independent of thinking,
set it to `high`. If the API only accepts `reasoning_effort` when thinking is
enabled, keep thinking disabled and do not send the reasoning field.

### Fixed validation setup

Validate each generated UAF corpus with the same 8-VM, 12-hour validation
budget:

```text
validate VMs: 8
validate duration: 12 hours
target_match_mode: sn-fallback
sn_fallback_range: 2
enable_replay: true
enable_varname_scheduling: true
priority_low_history: true
disable_collection_delay: true
disable_verify_delay: true
disable_access_delay: false
require_origin_match: false
origin_match_mode: varname
max_stable_pairs_per_origin: 1
max_stable_pairs_per_entry: 16
enable_history_minimization: false
verify_repeat_times: 1
repeat_count: 1
```

Report validation yield with both raw and deduplicated counts:

- processed entries
- entries with no stable runtime pairs
- handled pairs
- executed verify pairs
- skipped pairs
- confirmed DATARACE crashes
- unique DATARACE VarName pairs
- strict-SN / SN-range / stack-only success split
- time to first confirmed race
